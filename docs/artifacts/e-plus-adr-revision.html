Conversation Mode: Session Attachment

Two structural constraints, two surviving shapes, one product principle.

Problem, restated

Any design for a voice conversation over an active Claude Code session runs into two structural constraints of Claude Code itself. The original ADR walked through four options; only these two constraints did the actual work of ruling any option out. Naming them explicitly reduces the four-option table to two facts:

Wall 1 · No foreground command spans turns

A slash command or user-side entry point is bound by the session's turn model: it's a prompt, the assistant responds, the turn closes. /vox:talk could open the mic and drive one exchange, but the moment the LLM finishes its reply the command has exited. There is no primitive to hold a command alive across multiple turns. This rules out barge-in and multi-turn as a foreground shape.

Wall 2 · No background process can inject

Push the mic loop outside the session and the transcript has to reach the session somehow. Claude Code exposes no channel by which an external process can hand a user turn in. Hooks are reactive to internal events; the interactive loop is TTY-driven; there is no injection surface a background process can push into.

Every survivable design has to avoid both walls. There are only two ways to do that:

The two survivable shapes. Either (a) collapse the multi-turn voice conversation into a single Claude turn — so Wall 1 doesn't apply because there's only one turn — or (b) run the voice conversation in a peer process against the same session's stored state — so Wall 2 doesn't apply because there's no injection.

Option D in the original ADR is (b). Option E+, added here, is (a).

Two surviving options

Option DPeer subprocess per turn

Shape (b)

Design

Per turn, spawn claude -p --resume <id> --input-format stream-json --output-format stream-json --bare. Same session ID as the interactive session, separate process. Voxd on the audio-hardware machine owns mic, TurnDetector, STT, TTS, and playback; the subprocess spawn happens on whichever machine hosts vox call.

Pros

  • Reuses Claude Code's own engine; no reimplementation of tools, permissions, or context.
  • Voice agent has access to whatever tools the primary session has, via claude itself.
  • Bounded new work — the mechanism is a supported CLI invocation.

Cons

  • 13-25s per-turn cold start motivates --bare, which requires ANTHROPIC_API_KEY (no OAuth path).
  • Concurrent-resume safety against the live session is unverified; the original ADR flags it as Slice 1b's blocking spike.
  • A third process (the subprocess) per turn adds spawn overhead and lifecycle management.
  • Voice call's context is exactly the session's stored history — no continuous update possible during the call.

Option E+Voxd hosts the voice agent; context stays warm via hook fanout

Shape (a)

Design

/vox:talk is a blocking Claude Code tool call. Voxd hosts the voice agent (via ElevenLabs Conversational AI). Rolling per-session context is maintained inside voxd by the hook fanout that already exists for TTS chimes. Voice-agent tools reach code via quarryd's REST API. When the call ends, transcript and any notes return as the tool's value.

Design elements

  • Hook fanout carries context, not just TTS. Every Claude Code hook that reaches voxd via mcp-proxy --hook for chime purposes carries a payload with the relevant session state. Voxd retains those payloads in a rolling per-session transcript store alongside whatever TTS action the hook triggers. No new hook; no new wire.
  • Voxd instantiates the voice agent with warm context. On /vox:talk, voxd starts an EL Conversational AI session with a system prompt (voice-first, tool-friendly), a rolling context (recent turns raw + running summary), and a small tool surface.
  • Voxd implements the voice-agent's tools by dialing services. search_code(query) → quarryd's REST API over the WAN. read_recent_conversation(n), read_older_conversation(query) → local reads over voxd's rolling store. write_note(text) → append to a per-call note file returned in the tool result.
  • The voice call is one Claude turn. /vox:talk blocks; multi-turn happens inside voxd. Return value is transcript + notes. Wall 1 is not violated because there is only one Claude turn.

Pros

  • Sub-second per-turn latency via EL streaming — no claude subprocess cold-start.
  • No --bare; OAuth-only setups work — voxd owns its own LLM API key.
  • No concurrent-writer risk; voxd's transcript is independent of Claude Code's session storage.
  • Warm context: fanout maintains it, so voxd's LLM knows what the primary session was just doing.
  • Notes and transcript surface as tool return value for the primary session to act on afterward.

Cons

  • Voxd hosts a rolling-context store — new work, well-understood chat + retrieval territory.
  • Vendor coupling to ElevenLabs Conversational AI.
  • Hook reliability matters. A dropped hook creates a context hole. Design needs an idempotent monotonic sequence + gap-resync between Claude Code hooks and voxd.
  • Voice agent has no direct access to the primary session's tools. Depends on accepting the design principle below.

Recommendation

Adopt Option E+ if the streaming voice work already targets ElevenLabs Conversational AI

The rolling-context store is bounded new work. The hook fanout already exists as a pipe — voxd is just retaining what today it discards after playing the chime. The wins are durable: sub-second per-turn latency, OAuth-compatible, no concurrent-writer risk, and a natural return channel through the tool call's value.

If the schedule cannot absorb the rolling-context work this cycle, Option D remains a working design; its costs are real but its infrastructure exists. Nothing about E+ invalidates D as a fallback.

Load-bearing product principle

One agent at a time. Voice is read-mostly.

During a call, the primary Claude Code session is blocked in /vox:talk. The voice agent has read access to code (via quarry) and to recent conversation (via voxd's rolling store) but has no write access to the primary session or its tools. Anything action-worthy that emerges from the call returns as write_note output, for the primary session to act on when it resumes.

This is stated as a first-class design principle, not a limitation. It buys three properties that fall out of nothing else:

  • No concurrent-writer risk — the primary session's storage is untouched.
  • No attention-splitting — the user is on one channel at a time.
  • No risk of destructive tool calls initiated by voice — voice is a good modality for exploration, a bad modality for irreversible actions.

Naming this principle in the ADR is the load-bearing decision. Everything else in Option E+ falls out of it.

Superseded & carry-forward

Options A, B, C from the original ADR remain rejected, but the framing shifts. A and B fail Wall 2 (no injection surface); C fails FR-4 as originally stated — but E+ is the shape C wanted to be. C imagined running the agent inside voxd with a parallel context; E+ delivers that shape with the two ingredients C lacked: warm context via hook fanout, and code access via quarry. Rejecting C in the original ADR was correct at the time; adopting E+ now is not a reversal of that rejection, it is what becomes possible once those two ingredients are added.

The Open Risk on concurrent-resume safety (original Slice 1b) becomes moot under E+ and stays live under D.

Sequencing under Option E+

  1. Streaming ADR commits to ElevenLabs Conversational AI as the voice-agent vendor. Voxd's /call/<id> event-stream WebSocket contract carries typed JSON events between voxd and the dev-box client — no PCM on the wire.
  2. Voxd owns mic + STT + TTS + speakers. Mic capture, TurnDetector, and STT provider move from vox call's wiring into voxd. Package layout already matches.
  3. Voxd gains a rolling per-session context store plus a small tool broker (search_code, read_recent_conversation, read_older_conversation, write_note).
  4. Claude Code hooks route through mcp-proxy --hook. Hook payloads reach voxd both for TTS action and for context retention. Add a monotonic sequence + gap-resync mechanism between Claude Code and voxd so context holes are detectable.
  5. Voxd's tool implementations dial quarryd's REST API for search_code. Same TLS + bearer + profile pattern mcp-proxy uses; no MCP required.
  6. /vox:talk is added as a Claude Code slash command or blocking MCP tool. Returns transcript + notes on completion. Multi-turn happens inside voxd; Claude Code sees one turn.
  7. Option D remains buildable as a fallback for as long as it's cheap to keep. It becomes the go-to shape only if E+'s hook-fanout reliability cannot be brought up to load-bearing quality.
