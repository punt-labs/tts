Vox voice — Option E+

The voice agent lives inside voxd, backed by ElevenLabs Conversational AI. Rolling per-session context stays warm via the same hook fanout that already delivers TTS chimes. The voice agent reaches code via quarryd REST, and can launch a fresh claude, pi, or opencode session from the conversation itself.

ContinuousHook fanout — steady-state, not just during calls

H
Every hook payload reaches voxd and is retainedExisting sessions (Claude Code, and Mode-B-spawned sessions after they start) send SessionStart, PromptSubmit, PostToolUse, Stop, Notification, etc. through mcp-proxy --hook. Voxd both takes the TTS action (existing) and appends the payload to the rolling context store keyed by session (new).

Mode ASession-attached — existing Claude Code session opens the mic

A1
Claude Code invokes /vox:talkSlash command or MCP tool. Blocks the primary session's turn for the duration of the call.
A2
mcp-proxy → WAN → voxdWebSocket message on /mcp. First and only WAN hop for control.
A3
Voxd starts EL Conv AI session with warm contextRolling store seeds recent turns + running summary. Tool broker registers search_code, read_recent_conversation, read_older_conversation, write_note. In Mode A, launch_session is typically unregistered — the session already exists.
A4
Voice conversation runs inside voxdMic → EL Conv AI → tools as needed → TTS → speakers. Multi-turn happens here. The Claude Code turn model is not crossed because Claude Code still sees exactly one turn.
A5
Call ends → transcript + notes as tool return/vox:talk returns. The primary Claude Code session resumes with the transcript and any write_note outputs in view.

Mode BVoice-first — user speaks to voxd; voxd spawns the session

B1
User initiates the call at the laptopWake word, hotkey, or vox call from a terminal on the laptop. No prior coding session exists.
B2
Voxd starts EL Conv AI session (cold context)No warm hook-fanout seed for this call — this is the entry point. Rolling context store may contribute cross-session notes if voxd is configured for that; otherwise the conversation starts clean. Tool broker registers search_code, write_note, and launch_session.
B3
Voice agent calls launch_session(agent, task, host?)v1 default — same host: voxd forks a fresh claude, pi, or opencode into a detached tmux on its own machine (the laptop). No SSH, no WAN hop, no host registry — just subprocess + tmux. v2 optional — SSH remote: supply a host argument and voxd resolves it against a registered-hosts config, then ssh-execs into a detached tmux there. Use v2 when the user's project lives on the dev-box, not the laptop.
B4
Spawned session's hooks route back to voxdThe launched session uses mcp-proxy --hook the same way any Claude Code session would. In v1 that's a localhost loopback (no auth needed if voxd binds to 127.0.0.1); in v2 it's the same WAN path Mode A uses. Its hook payloads join the rolling context store, and voxd's voice agent can narrate progress or take further actions in the same call — no primary session to compete with.
B5
User attaches or reviews laterThe spawned session lives in a detached tmux; the user attaches from the dev-box terminal when convenient. Voice-first mode is "kick something off by voice", not "drive an IDE by voice."

Load-bearing principles

Voxd is the voice-agent host, and the coding-session launcher.

Both modes converge on the same interior: one EL Conv AI session, one tool broker, one rolling context store. The only difference is whether a primary coding session pre-exists (Mode A) or gets spawned mid-call (Mode B). Consumers see one voice architecture with two entry points, not two architectures.

Same host first; SSH is a v2 layer, not a v1 requirement.

launch_session with no host forks locally on the voxd host — no SSH, no host registry, no auth. That's v1. A registered-hosts config and ssh exec come later, when someone actually wants to voice-launch onto a remote box. Same tool signature; the API doesn't change when SSH is added.

One agent at a time.

During a call, the user is talking to voxd's voice agent — nothing else. In Mode A the primary Claude Code session is blocked in /vox:talk; in Mode B no primary session exists yet, or the spawned one is fresh and running headless. Voice is read-mostly against any primary session's tools, and any writes it initiates go through the tool broker's small, deliberate surface.

Latency budget is inside voxd, not per turn.

No claude -p --resume --bare spawn between the user's speech and the reply. EL Conv AI streams end-to-end. Per-turn cost is dominated by the streaming service, not by cold-starts on either side.

Context is a fanout, not a fetch.

The rolling context store is fed by hook payloads flowing continuously from every mcp-proxy-connected session — including Mode-B-spawned sessions once they start. The voice agent reads from the store, never blocks on remote history retrieval, and stays available for barge-in throughout.
